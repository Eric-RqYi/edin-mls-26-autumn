# Task 3/4 最终实验结果汇总

**数据复用与执行粒度的改进带来了明确的内核及系统收益，但更大的计算范围并非适合所有形状。**形状特化主要用于修补例外，不能代替对主要成本的优化。当前结果足以围绕“复用收益—并行与资源代价—形状边界—系统收益”组织报告，无需继续堆叠新的优化点。

本目录汇总 2026-11-18/19 的任务 A、B，使用各次运行的原始数据和冻结验证器重新核验，未改写原始结果，也未修改正在编辑的 `report/draft.md`。

## 最重要的结果

| 证据层级 | 对照与结论 | 结果 |
|---|---|---|
| 通用 GEMM，既有受控系统实验 | 固定 M=1 路径，tiled16 → rb4x4 | ASR 5942.23 → 3381.82 ms，配对 **1.757×**，延迟减少 **43.09%** |
| A：纯 warp 调整 | 在 rb4x4 + M1/w4 上，attention 4 → 16 warp | ASR 3372.00 → 3129.04 ms，配对 **1.07756×**，延迟减少 **7.21%** |
| A：窄 N 分派 | 同一 A baseline 上增加固定分派规则 | ASR 3336.70 ms，延迟减少 **1.05%** |
| A：组合 | 同时使用 warp 调整与窄 N 分派 | ASR **3093.89 ms**，配对 **1.08985×**，延迟减少 **8.25%** |
| B：30 条多音频 | 原始 tiled16/M1 关闭/4 warp → 最终优化包 | 核心 ASR 配对 **1.98455×**，每 query 的配对节省中位数 **3.932 s** |
| B：真实完整 RAG | 同一 query、同一轮完整执行两种版本 | 配对 **1.46092×**，配对节省中位数 **3.760 s**，95% query-bootstrap CI **[3.230, 4.341] s** |

**这些行使用不同 baseline、音频集合及 allocation，不相加或连乘。**A 用于拆分因素，B 用于检验整体优化包的多音频系统价值。B 的正式生成请求 180 次，加预热共 184 次，无失败、无 SDK 重试；每条音频每版本三次，统计单位为 30 条 query，而不是 90 次独立样本。

## A：报告主线所需的边界证据

- Encoder Q/FC1/FC2 的 rb4x4 局部配对加速约 **2.71/2.70/2.69×**。新定向扫描中，rb4x4 在 37 个 case 中快于 tiled16 的有 20 个、慢的有 17 个；这个数量没有按模型调用频率加权。
- N=K=2048 时，rb4x4 在 M=64 为 **0.303819 ms**，M=65 为 **0.455877 ms**：多一行，耗时增加约 **50.05%**。64 行输出 tile 的有效槽位比例从 100% 降到约 50.8%，形成解释边界的直接证据。
- `(M,N,K)=(32,256,2048)` 中，rb4x4 的逻辑有效元素加载请求从 tiled16 的 **8.389 MB 降至 3.146 MB**，但耗时反而从 **0.047816 增至 0.163595 ms**。Grid 从 32 个 block 降为 4 个，在 16 SM 的设备上暴露了并行任务不足；资源需求和尾部浪费也同时改变。逻辑请求量不是实测 DRAM 流量，不据此声称 memory-bound。
- M=1 三路径独立构建：lm_head 中 tiled16 **4.057806 ms**、未经特化 rb4x4 **5.812040 ms**、M1 专用路径 **0.886454 ms**。专用路径相对前两者分别约 **4.58×、6.56×**；不能拿旧六配置中共用同一路径的 M=1 行来证明原始 rb4x4 在 M=1 上更快。
- Attention：T=1500、D64 的 16 warp 相对 4 warp 约 **1.321×**；T=32 的最佳配置却是 8 warp。D128 causal 的 T=64 选 16 warp 更快，T=65 则是 8 warp 更快。统一扩大 block 工作范围有效，但有长度与尾部边界。

A 的新增四组 ASR 结果取代此前组合配置的系统收益数字。三组模型进程排序一致，全部 150 次计时生成的 token 一致，形状与原算子事件总和的 30 项核对差值均为零。

## B：系统价值与质量结论的范围

| 音频层（各 10 条） | 时长范围 s | ASR 配对加速 | 完整 RAG 配对加速 | 完整 RAG 配对节省中位数 s |
|---|---:|---:|---:|---:|
| 短 | 3.700–4.825 | 1.872× | 1.328× | 2.654 |
| 中 | 4.950–6.075 | 1.989× | 1.538× | 3.897 |
| 长 | 6.200–8.425 | 2.174× | 1.527× | 5.825 |

所有 query 内，两个版本及三轮重复的 **token、转写、embedding、检索 scores/排名、context、prompt 一致率均为 100%**（浮点向量/分数按既定容差）。180 次正式 ASR 均正常 EOS，无截断。检索指标完全相同：**Recall@5=0.402381，MRR@5=0.475000，NDCG@5=0.393857**。没有人工参考转写或答案评审，不把这些结果扩展为 WER/CER 或答案质量得分不变。

**音频秒数不等于 encoder 计算长度。**所有请求的输入 features 为 `[1,128,3000]`；三层代表音频的诊断 encoder 均为 1500。变化主要来自 decoder prompt 长度与生成 token 数；不能把长音频更大的加速直接归因于 encoder 更长。

完整请求的收益被其余阶段稀释。90 次正式请求/版本的算术平均：总耗时 **13.973 → 9.994 s**，其中核心 ASR **8.410 → 4.212 s**，ELM 响应约 **4.990 → 4.977 s**。这些平均值来自同批真实完整请求，仅用于阶段占比解释，不用独立阶段中位数拼接“总耗时”。

有一条长音频 query 的完整请求配对中位数回归约 **6.362 s**；预处理和 query encoding 出现秒级本地长尾，并非只有 API 波动。所有慢样本保留。整体端到端置信区间为正，分层 query-bootstrap 敏感性检查也为正，但不能保证每条 query 或每种服务负载都加速。

可直接用于结论段的表述：

> 扩大线程和线程块负责的计算范围，可通过提高片上数据复用降低主要负载的延迟，但收益受到资源需求、可并行 block 数与 tile 尾部利用率限制。M1 和窄 N 专用路径改善了部分例外，不能说明更复杂的形状分派普遍更优。在预先抽样的 30 条音频上，最终优化包使核心 ASR 配对加速约 1.985×，真实完整 RAG 请求约 1.461×；输入与检索证据保持一致。系统收益小于内核收益，且部分请求仍受本地与服务端延迟波动影响。
