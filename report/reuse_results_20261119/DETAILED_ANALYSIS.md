## 3. GEMM：真实收益与适用边界

### 3.1 主要真实形状受益

既有受控形状表支持 encoder Q/FC1/FC2 的 rb4x4 约 2.71/2.70/2.69× 加速。固定 M1 路径的完整模型从 tiled16 5942.23 ms 降至 rb4x4 3381.82 ms，配对 1.757×、延迟下降 43.09%。这是独立运行的结果，不与新实验的 raw time 拼接成一次测量。

rb4x4 让一个线程维护 16 个输出累加器，block 输出从 16×16 扩至 64×64。共享数据可参与更多乘加，同时改变 global 请求规模、grid 和尾部浪费。因此实验支持“复用与执行粒度的联合改进”，不是仅改变一个因素的纯寄存器复用实验。

| 实现 | Registers/thread | 静态 shared bytes/block | Spill |
|---|---:|---:|---:|
| tiled16 | 32 | 2112 | 0 |
| tiled32 | 32 | 8320 | 0 |
| rb2x2 | 40 | 4224 | 0 |
| rb2x4 | 48 | 6400 | 0 |
| rb4x4 | 56 | 8448 | 0 |

这些是 ptxas 编译器证据，没有测量实际 occupancy、stall 或 DRAM 指标。不能仅用“寄存器较少”或“occupancy 较高”解释性能。

### 3.2 定向边界说明收益并非普适

37 个定向 case 中 rb4x4 胜于 tiled16 的有 20 个，慢的有 17 个。这个比例不能当成模型工作负载的平均加速，因为不同形状的调用数和累计耗时差异很大。

- N=K=2048、M=16：rb4x4 0.279298 ms，tiled16 0.179739 ms；只有 16 行却计算 64 行 tile，较大的粒度不利。
- M=31/32：tiled32 比 rb4x4 更快；M=33：rb4x4 变为 1.570× tiled16，而 tiled32 只有 0.896×。不同 tile 边界形成不同台阶。
- M=64→65：rb4x4 的 64 行 tile 从一排变为两排，输出槽位利用率从 100% 到 65/128；耗时 0.303819→0.455877 ms，约增 50.05%。这不只是 FLOP 数增加一行的平滑效应。
- M=32,N=256：rb4x4 的 grid 只有 4 blocks，而 tiled16 有 32 blocks；前者在 16 SM 上可并行 block 数不足。逻辑有效元素加载请求减少 62.5%（8.389→3.146 MB），却慢约 3.42 倍。它直接反驳“请求更少就一定更快”。请求模型忽略缓存、实际事务和指令调度，不能当成实际 DRAM 流量。

这些是围绕已知边界的定向验证，不应包装为此前未见过的独立选型测试集。

### 3.3 窄 N 特化改善部分例外，并非通用规则

N=512,K=2048 时，M=32/64 的 tiled32 分派相对 rb4x4 分别约 2.37/1.34×；M=65/96 中分派反而使独立微基准耗时增加约 9.5/9.7%。N=256 不满足规则，仍保留 rb4x4 的退化；K 邻近控制也保留原路径。

本轮没有根据结果追加分派规则。完整 A 模型的 hybrid 单项节省约 35.30 ms，说明当前真实路径净受益，但不能据此把所有窄 N 都归入同一最优实现。微基准热缓存与模型交替权重、分配/launch 的事件边界不同；是否进一步细分应做新的直接 A/B，不能只挑局部冠军。

### 3.4 M=1 必须是独立路径对照

| M=1 形状 | tiled16、特化关闭 ms | rb4x4、特化关闭 ms | M1 专用 ms | 相对 tiled16 配对加速 |
|---|---:|---:|---:|---:|
| N=512,K=2048 | 0.045821 | 0.154459 | 0.005850 | 7.833× |
| lm_head：N=59264,K=2048 | 4.057806 | 5.812040 | 0.886454 | 4.577× |

M1 专用相对原始 rb4x4 分别约 26.4×、6.56×。原始 rb4x4 在只有一行时的 tile 浪费说明，扩大统一计算粒度有明确例外。

这里测的是局部收益；A 的系统四组均开启 M1，并未重新隔离其系统贡献。B 也只比较整体优化包。不能把 lm_head 4.58× 写成完整系统 4.58×。

## 4. Attention：执行粒度在不同负载上的效果

| 负载 | 4 warp ms | 16 warp ms | 16 warp 配对加速 | 最佳已测配置 |
|---|---:|---:|---:|---|
| Encoder-style T=32,D64 | 0.020590 | 0.016806 | 1.225× | 8 warp（1.269×） |
| T=128,D64 | 0.234798 | 0.174107 | 1.349× | 16 warp |
| T=512,D64 | 3.534440 | 2.650091 | 1.334× | 16 warp |
| Encoder T=1500,D64 | 29.861917 | 22.601063 | 1.321× | 16 warp |
| Decoder causal T=64,D128 | 0.079301 | 0.049611 | 1.598× | 16 warp |
| Causal T=65,D128 | 0.094341 | 0.071200 | 1.325× | 8 warp（1.380×） |

长 encoder 中，query block 数由 ceil(1500/4)=375 降为 ceil(1500/16)=94，每份 KV tile 可服务更多 query；代码层面的 KV 重复加载请求减少约四倍。但 block 线程数也从 128 增至 512，短序列和尾部可能暴露资源与并行度代价。没有硬件计数器时，不把请求减少写成 DRAM 流量减少四倍。

新增 T=32/128/512 是合成的 encoder-style 诊断负载，不是声称 RAG 音频产生了这些 encoder 长度。单 query/cache case 也是低并行度压力条件，不是当前无 KV cache 的实际 decoder 路径。图 2 分开显示这些条件。

## 6. B 的多音频完整系统结果

先在每条 query 内对三轮配对测量求中位数，再对 30 条 query 统计。Bootstrap 固定 seed=21、2000 次 query-cluster 重采样；以下区间对应节省毫秒的中位数。

| 指标 | 每 query baseline 中位数的总体中位 s | Final 对应值 s | 配对节省中位 s | 配对加速 | 95% 节省 CI s |
|---|---:|---:|---:|---:|---|
| 核心 ASR | 7.865 | 3.983 | 3.932 | 1.985× | [3.437,4.401] |
| 真实完整 RAG | 12.729 | 8.440 | 3.760 | 1.461× | [3.230,4.341] |

“中位数之差”“配对差值的中位数”“比值的中位数”是不同统计量，表中各列不强行相减/相除互推。完整 RAG 包含音频读取、预处理、ASR、IPC、CPU encoding、检索、context/prompt 与真实 ELM 响应。

保持短/中/长每层十条的额外分层 query-bootstrap 检查中，ASR 节省区间为 [3.743,4.170] s，RAG 为 [3.361,4.336] s，均为正。主结果使用冻结汇总器的原统计口径，敏感性检查另列，没有挑选更好看的区间替换主结果。

短/中/长 ASR 配对加速分别为 1.872/1.989/2.174×，完整请求为 1.328/1.538/1.527×。所有请求 features 均为 `[1,128,3000]`；三个长度层各一条代表的独立诊断 encoder 均为 1500，decoder 初始长度为 61/77/102。生成 token 数覆盖短层 10–16、中层 14–19、长层 17–26。不同层不是只改变音频秒数的单因素实验；不能从层间相关性唯一归因于某一 shape。

### 6.1 为什么 ASR 约两倍，完整请求只有约 1.46 倍

下表是同批 90 次正式完整请求/版本的算术平均，含所有长尾；各阶段可相加只是平均数的线性性质，不是用阶段中位数合成一个未测量的请求。

| 阶段 | Original mean s | Final mean s |
|---|---:|---:|
| 核心 ASR | 8.410 | 4.212 |
| ASR 其余部分（读取/处理/IPC 等） | 0.223 | 0.255 |
| 本地 RAG 与残差 | 0.350 | 0.550 |
| ELM 响应 | 4.990 | 4.977 |
| 实测总请求 | 13.973 | 9.994 |

ELM 响应平均时间几乎不变，ASR 优化不能直接缩短它。优化后 ELM 约占平均总时间的一半，形成整体收益的边界。回答长度和服务端等待也会波动，当前没有接口暴露的缓存 token 数或 request ID，不能推断服务端没有缓存或没有内部重试。

RAG 组件 startup 约 354.18 s，ASR worker startup roundtrip 约 352.01 s；两者是独立环境的加载成本，未纳入 warm inference 比较，也不是两版本各自的 startup A/B。不能将约 1.46× 外推为含冷启动的首次请求收益。

### 6.2 不回避长尾和负结果

全部 30 条 query 的 ASR 配对中位节省为正；完整 RAG 为 29 条正、一条负。负例 `q_94efba4b07bc12eb` 时长 7.0 s、生成 23 tokens，三轮端到端节省为 -20.711/-6.362/+5.553 s，配对中位为 -6.362 s。

其第一轮 final 实测总耗时 41.491 s，其中预处理 11.253 s、query encoding 13.305 s、核心 ASR 7.554 s、ELM 响应 7.682 s。第二轮也有 query encoding 9.056 s。本地阶段的长尾显著，不能把全部回归归因于 API。原始记录没有足够计数器区分 CPU 调度、文件/内存访问、线程竞争或其他等待；不为解释结果臆断具体原因。

Original/final 的 query encoding mean 为 0.342/0.520 s，而 median 均约 18 ms；两者差距也表明长尾的重要性。原始数据和 `b_largest_local_delays.csv` 保留这些请求，不做去异常后的冠军统计。

整体区间为正说明在这 30 条、这次 allocation 和 API 时间窗口内，完整系统收益可辨识。它不证明每条音频、所有系统负载或其他 GPU 都受益。

|---|---:|---:|---:|---:|
| Original | 30 | 0.402381 | 0.475000 | 0.393857 |

这些指标证明本样本上输入与检索证据未改变，不证明答案质量分数已验证。ELM 即使接收相同 prompt 也可以返回不同长度/措辞的回答；平均生成 tokens 为 265.42/262.80。没有 judge，不把回答随机变化归因于 CUDA；没有人工转写，不报告 WER/CER。

## 8. 报告组织建议及尚存限制

建议按以下逻辑写作，而不是按实现改动的时间顺序罗列：

1. 主要 workload 的成本分布决定优化优先级；M1 的局部特化价值与系统占比是两回事。
2. GEMM 扩大每线程/每 block 计算范围，在主要形状上获得大收益；资源和边界表解释反例。
3. 在 attention 中检验相似的 block 复用思路，展示长度条件和纯 warp 的系统对照。
4. M1/窄 N 用于修补已观察到的例外，其额外价值有限但解释清楚。
5. 多音频完整请求确认整体优化包的系统价值，最后用阶段占比和长尾解释为什么系统加速更小。

图 1/2 为 A 的两个正文候选图；图 3/4 为 B 的阶段和 query 级候选图。A 四组 ASR 表可直接从 CSV 取数。完整表放复现材料，不在六页正文堆全部扫参结果。

尚存限制：单型号 MIG、每组一次 allocation、每 query 三轮、只选 30 条 dev；诊断 profile 只覆盖每层代表；没有 DRAM/stall 实测，不能证明唯一机制；原音频/corpus/enc_a 大文件不在本地，只能重建冻结抽样框，不能重算所有资产 hash；没有转写人工参考和答案 judge。无需为了补一个额外小加速继续扩大搜索。若要增强稳健性，后续优先跨 allocation 复测已冻结配置并诊断本地长尾，ELM 请求必须另有明确预算。

## 9. 复核方法与产物

`collect_results.py` 对 A 每部分启动隔离进程，使用各自冻结验证器；B 在临时副本中运行冻结汇总器，避免重写保存的结果。所有输入在分析前记录 SHA256、输出后再次核对。`input_sha256.json` 共覆盖 418 个输入文件（含历史 GEMM），全部保持不变。脚本不调用 ASR、GPU kernel 或 ELM。

数据表、metrics.json、四张 PNG/矢量 PDF、绘图脚本均在本目录。`report/draft.md` 和其他正在编辑的文件未修改。重跑时可指定原始 A/B 根目录；若历史 GEMM 原始目录不在本地，会保留 A 中已存的历史表，但不会声称重新审计了缺失原始文件。
